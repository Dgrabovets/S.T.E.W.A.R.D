# Status

Общий формат статуса процессов и раннер, который запускает задачи. Это библиотека без интерфейса: её используют приложение в трее (`Steward`) и сами процессы, например `Steward.Mail`.

## Как это работает

1. В `config/jobs.json` перечислены задачи: что запускать и когда.
2. Приложение в трее при старте и каждые полминуты проверяет условия и запускает то, чему пора.
3. Каждая задача пишет свой статус в `data/status/<id>.json`. Если не написала, это делает раннер по коду завершения.
4. Приложение читает все файлы из `data/status/` и показывает строку на каждую задачу: цвет, короткий статус и подробности.

Расписание пар из Google Таблицы в этот список не входит: им занимается Docker, а приложение читает его журнал отдельно.

## Файл статуса

`data/status/<id>.json`, имя файла равно `id`.

```json
{
  "schemaVersion": 1,
  "id": "mail",
  "title": "Почта",
  "state": "ok",
  "updatedAt": "2026-10-25T09:00:03+01:00",
  "lastRunAt": "2026-10-25T09:00:03+01:00",
  "lastSuccessAt": "2026-10-25T09:00:03+01:00",
  "nextRunAt": null,
  "summary": "Новых важных писем нет",
  "error": null,
  "awaiting": 0
}
```

| Поле | Смысл |
|---|---|
| `id` | Латиница в нижнем регистре, цифры, дефис и подчёркивание, до 64 символов |
| `state` | `idle`, `running`, `ok`, `needsAttention` или `failed`. Незнакомое значение читается как неизвестное и показывается нейтрально |
| `updatedAt` | Когда файл записан. По нему раннер понимает, что процесс сам обновил статус |
| `lastRunAt` | Когда был последний запуск. От него считаются интервалы и пропущенные запуски |
| `lastSuccessAt` | Когда запуск последний раз удался. Если процесс упал, прошлое значение сохраняется |
| `summary`, `error` | Итог и текст ошибки одной строкой |
| `awaiting` | Сколько результатов ждёт решения пользователя: идеи, черновики ДЗ. Не ноль, значит строка жёлтая |

Правила для процесса, который пишет статус сам:
- Пиши целиком и атомарно: `StatusStore.Write` делает это через временный файл. Чтобы не терять прошлый успех и число ожидающих, пользуйся `StatusStore.Report`: он дописывает их из прежнего статуса.
- Папку статусов бери из `DataLocation.StatusDirectory()`: раннер передаёт её в переменной окружения `STEWARD_DATA`, а при ручном запуске она находится от `Steward.slnx`.
- Не пишешь статус, ничего страшного: раннер запишет `ok` или `failed` по коду завершения.

## config/jobs.json

```json
{
  "jobs": [
    {
      "id": "mail",
      "title": "Почта",
      "enabled": false,
      "command": "{repo}\\Steward.Mail\\publish\\Steward.Mail.exe",
      "arguments": "",
      "triggers": [
        { "type": "start" },
        { "type": "daily", "at": "09:00" },
        { "type": "daily", "at": "19:00" }
      ],
      "timeoutMinutes": 10,
      "staleAfterMinutes": 960
    }
  ]
}
```

- `{repo}` заменяется корнем репозитория.
- Условия запуска: `start` (при запуске приложения), `daily` (каждый день в `HH:mm` по местному времени), `interval` (через `everyMinutes` минут после прошлого запуска).
- `enabled: false` отключает автозапуск, но задачу можно запустить кнопкой.
- `timeoutMinutes` останавливает зависший процесс. `staleAfterMinutes` делает строку красной, если давно не было успеха.
- В файле можно писать комментарии. Плохая задача пропускается, остальные работают, а ошибка видна в разделе «Статус».

Правила раннера:
- **Старт.** Условие `start` срабатывает один раз за запуск приложения и пропускается, если задача уже запускалась меньше десяти минут назад.
- **Пропущенное.** Запуск `daily`, который пропущен из-за выключенного компьютера, выполняется один раз при следующем старте.
- **Время.** Времена `daily` считаются по местным часам, поэтому переход на зимнее и летнее время их не сдвигает.
- **Один экземпляр.** Одна задача не запускается дважды одновременно.
- **Среда.** Процесс получает `STEWARD_DATA`, а `TEMP` и `TMP` указывают в `data/tmp`, чтобы временные файлы не попадали на системный диск.

## Папка data

`data/` в корне репозитория (в `.gitignore`): `status/` с файлами статусов, `runs.jsonl` с журналом запусков, `tmp/` для временных файлов, `last-notified.txt` с меткой последнего уведомления. Другое место задаётся переменной `STEWARD_DATA`, а другой файл задач переменной `STEWARD_JOBS`.

## Проверка

```bash
dotnet test tests/Steward.Status.Tests
```

Тесты запускают настоящие дочерние процессы (`cmd` и `powershell`) и проверяют день перехода на зимнее время.
